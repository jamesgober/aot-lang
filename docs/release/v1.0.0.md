# aot-lang v1.0.0 — stable

**1.0.** The public API is frozen and stable. v0.1.0 stood up the scaffold and the quality gates; v0.2.0 built the core — lowering an `ir-lang` function to object code and laying functions out into a single linked image. This release ratifies that surface as the `1.0` contract: it follows Semantic Versioning, carries no breaking changes before `2.0`, and ships with the full test and benchmark suite verified across Linux, macOS, and Windows.

The public API does not change from `0.2.0` — a program that compiled then compiles identically now, to the same bytes. The release adds the stability documentation, hardens the object-code encoding, and expands the test suite and examples.

## What is aot-lang?

aot-lang is the ahead-of-time end of the `-lang` language-construction family. A front-end parses, type-checks, and lowers a program to the [`ir-lang`](https://docs.rs/ir-lang) intermediate representation; aot-lang compiles each function to object code with [`codegen-lang`](https://docs.rs/codegen-lang), encodes it, and lays the objects out with [`linker-lang`](https://docs.rs/linker-lang) into a single [`Image`](https://docs.rs/aot-lang) — a self-contained artifact with its code, a resolved symbol table, and an entry point. It is the batch counterpart to a just-in-time compiler: where a JIT runs a function the moment it is generated, aot-lang compiles the whole program up front.

```rust
use aot_lang::Compiler;
use ir_lang::{Builder, BinOp, Type};

// fn add(a: int, b: int) -> int { a + b }
let mut add = Builder::new("add", &[Type::Int, Type::Int], Type::Int);
let a = add.block_params(add.entry())[0];
let b = add.block_params(add.entry())[1];
let sum = add.bin(BinOp::Add, a, b);
add.ret(Some(sum));

let mut compiler = Compiler::new();
compiler.base_address(0x40_0000).entry("add");
compiler.add(&add.finish()).unwrap();
let image = compiler.link().unwrap();

assert_eq!(image.entry(), Some(0x40_0000));
assert_eq!(image.symbol("add"), Some(0x40_0000));
```

## The 1.0 surface

The frozen contract:

- **The shortcut** — `compile` lowers one function, links it at base address `0`, and returns an image with that function as the entry point.
- **The builder** — `Compiler` accumulates functions and links them into one image. `new`/`default` construct it; `base_address` and `entry` configure the layout; `add` compiles and appends a function; `link` produces the `Image`.
- **The error** — `AotError`, one variant per stage: `Codegen` (a function did not validate) and `Link` (a duplicate name or a missing entry point).
- **The result** — `Image` and `OutputSection` are re-exported from `linker-lang` as the output types.

`AotError` is `#[non_exhaustive]`, so a future stage that reports a new kind of failure adds a variant without a breaking change. The object-code encoding is fixed little-endian on every target, so the bytes for a given program are identical across hosts.

## SemVer promise

The crate follows [Semantic Versioning](https://semver.org):

- No documented item is removed or changed in a breaking way within `1.x`; breaking changes wait for `2.0`.
- New functionality is additive and arrives in minor releases. A new `AotError` variant is a minor change.
- The MSRV is Rust `1.85`; raising it is a minor change, never a patch.
- Behaviour is part of the contract: a function that compiles today keeps compiling, the object-code bytes for a given program are stable and identical across hosts, and the link-map `Display` form is unchanged for a given image.

The full statement lives in [`docs/API.md`](https://github.com/jamesgober/aot-lang/blob/main/docs/API.md#semver).

## Breaking changes

**None.** `1.0.0` makes no breaking change to the `0.2.0` surface.

## Hardening since 0.2.0

- **Exact, overflow-safe object-code sizing.** The encoder now computes the exact output length from the program before it allocates, so the buffer is allocated once and never grows — no reallocation on any input. The size is summed with saturating arithmetic, so the capacity computation cannot overflow even for a pathological program. A property test asserts the prediction is exact and that the buffer never reallocates; the hot encoding paths are `#[inline]`.
- **Expanded tests.** New coverage for base-address invariance (the base address shifts every symbol uniformly and leaves the code bytes untouched), many-function layout with a complete sorted symbol table, and symbol names carrying punctuation, alongside the encode/decode round-trip property and the code-generation and link error paths.
- **Runnable examples.** `compile_and_inspect`, `multi_function_image`, and `error_handling` demonstrate the surface end to end and run in CI.
- **Stability documentation.** The crate root, `README`, and `docs/API.md` now state the frozen `1.0` surface and the SemVer promise.

The property tests, error-path tests, and Criterion benchmarks shipped with `0.2.0` carry forward unchanged.

## Verification

Run on Linux (WSL2 Ubuntu) x86_64, Rust stable 1.95.x and the 1.85 MSRV toolchain; the CI matrix runs the full suite across Linux, macOS, and Windows at stable and 1.85:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --no-default-features --lib -- -D warnings
cargo test
cargo test --all-features
cargo test --no-default-features
cargo build --no-default-features        # genuine no_std build
cargo +1.85 build --no-default-features  # MSRV
cargo run --example compile_and_inspect
cargo run --example multi_function_image
cargo run --example error_handling
cargo bench --bench bench --no-run
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo deny check
```

All green. Test counts at this tag, identical across the default, `--all-features`, and `--no-default-features` builds:

- 16 unit tests, 8 integration tests, 10 documentation tests.
- 1 of the unit tests is a `proptest` property (encode/decode round-trip and exact sizing over generated functions).
- `cargo deny`: advisories, bans, licenses, sources all ok.

## What's next

The `1.0` surface is stable until `2.0`. Future work is documentation, tests, and internal optimization that does not change the public contract — plus the additive room the design leaves: cross-function references and relocations as `ir-lang` grows calls, wider machine types, and further object-code targets, each a minor release when it lands.
