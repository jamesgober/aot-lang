# aot-lang v0.2.0 — Core

**The first release with an implementation.** v0.2.0 turns the v0.1.0 scaffold into a working ahead-of-time compiler: it lowers [`ir-lang`](https://docs.rs/ir-lang) functions to object code and links them into a single image, wiring [`codegen-lang`](https://docs.rs/codegen-lang) and [`linker-lang`](https://docs.rs/linker-lang) into a two-stage pipeline. The public surface is `compile`, `Compiler`, and `AotError`, with `Image` and `OutputSection` re-exported as the result types — every item documented with runnable examples. No `unsafe`, `no_std`-capable, and green on all three platforms at the MSRV.

## What is aot-lang?

The ahead-of-time compiler of the `-lang` language-construction family. It takes functions in the `ir-lang` intermediate representation, lowers each to object code, and lays them out together into a single linked **image** — a self-contained artifact with its code, a symbol table, and an entry point, ready to be inspected, serialized, or loaded. It is the batch counterpart to a just-in-time compiler, and the end of the pipeline a front-end follows: parse, type-check, lower to IR, then compile the whole program ahead of time.

## What's new in 0.2.0

### The compile pipeline

A compile runs two stages, each backed by a wired dependency:

1. **Lower.** Every `ir_lang::Function` is checked with `Function::validate` and compiled to a `codegen_lang::Program` of register bytecode — the object code.
2. **Encode and link.** Each program is encoded into the bytes of a `.text` section with a symbol at its start, and `linker-lang` places the objects at addresses and resolves the entry point into the final `Image`.

### `compile` — the single-function shortcut

```rust
use aot_lang::compile;
use ir_lang::{Builder, BinOp, Type};

// fn square(x: int) -> int { x * x }
let mut b = Builder::new("square", &[Type::Int], Type::Int);
let x = b.block_params(b.entry())[0];
let sq = b.bin(BinOp::Mul, x, x);
b.ret(Some(sq));

let image = compile(&b.finish()).expect("square is well-formed");
assert_eq!(image.entry(), Some(0));
assert_eq!(image.symbol("square"), Some(0));
```

`compile` lowers one function, links it at base address `0`, and sets it as the entry point. It is the common case; the builder handles the rest.

### `Compiler` — several functions in one image

```rust
use aot_lang::Compiler;
use ir_lang::{Builder, Type};

let mut compiler = Compiler::new();
compiler.base_address(0x40_0000).entry("main");
for name in ["main", "helper", "table"] {
    let mut f = Builder::new(name, &[], Type::Unit);
    f.ret(None);
    compiler.add(&f.finish()).unwrap();
}
let image = compiler.link().unwrap();

assert_eq!(image.entry(), Some(0x40_0000));
assert_eq!(image.symbols().count(), 3);
```

Functions are placed in the order they are added, each defining a symbol under its own name. The base address and entry point are configurable; two functions with the same name collide and the link reports it.

### `AotError` — which stage failed

The failure type distinguishes the two stages instead of flattening them into one opaque message:

- `AotError::Codegen` — a function did not pass `Function::validate`.
- `AotError::Link` — a duplicate function name, or an entry point that was never added.

It implements `core::error::Error` with `source` set to the wrapped error, and converts from both underlying errors so `?` propagates them directly. The enum is `#[non_exhaustive]`.

### A deterministic object-code encoding

The lowered bytecode is flattened into a fixed, little-endian byte format — a header (register count, parameter registers, op count) followed by one record per op. The encoding is lossless, including `f64` bit patterns, and byte-identical across targets, so recompiling the same IR produces the same image everywhere. An encode/decode round-trip property test over generated functions guards the invariant, alongside targeted tests for the control-flow, unary, float, bool, and unit-return op records.

### Documentation

`docs/API.md` documents the full public surface — each item with a description, its parameters and return values, error semantics, and at least two runnable examples covering the happy path and the failure modes. The crate root and every public item carry rustdoc with examples that run as doctests.

## Breaking changes

**None.** This is the first release with a public API beyond the empty scaffold; everything here is new.

## Fixes since 0.1.0

- The `keywords` and `categories` fields in `Cargo.toml` were invalid TOML (unquoted), which blocked the manifest from parsing. Both are now correct string arrays, and the crate description was sharpened to match the implemented scope.
- The `clippy.toml` MSRV (`1.87`) disagreed with `Cargo.toml` (`1.85`); they are now aligned.

## Verification

Run on Windows x86_64 with the toolchain hosted in WSL2 Ubuntu (Rust stable 1.95.x); the same commands run in the CI matrix on Linux, macOS, and Windows at stable and the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --no-default-features --lib -- -D warnings
cargo test
cargo test --all-features
cargo test --no-default-features
cargo build --no-default-features        # genuine no_std build
cargo +1.85 build --no-default-features  # MSRV
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo deny check
```

All green. Test counts at this tag are identical across the default, `--all-features`, and `--no-default-features` builds:

- 16 unit tests (encoder round-trips and rejections, compiler layout and error paths).
- 5 integration tests (end-to-end compile of a loop, multi-function layout, stage-specific failures, reproducibility).
- 10 documentation tests.
- 1 of the unit tests is a `proptest` property (encode/decode round-trip over generated functions).
